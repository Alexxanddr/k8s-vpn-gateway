# ADR 001: authenticated pod-local overlay to a single shared gateway

Status: implemented; experimental pending the complete acceptance matrix.

## Context

The inspected deployment target uses Flannel VXLAN with kube-proxy. Flannel does
not expose a native per-workload VPN egress gateway API. Existing NetworkPolicy
objects do not establish that an enforcing policy engine is installed. Native
CNI egress gateways in other CNIs would introduce a different dependency and
potential node routing changes. This version does not depend on them.

[pod-gateway](https://github.com/angelnu/pod-gateway) demonstrates an overlay
between clients and a shared gateway using VXLAN and DHCP. A raw VXLAN transport
would require peer addressing/discovery and would not authenticate other cluster
workloads. [Gluetun](https://github.com/passteque/gluetun) supplies a provider VPN
and a firewall; its OUTPUT protection alone is not a FORWARD policy for other Pods.

## Decision

Use standard OpenVPN in TLS server/client mode as the **internal IP overlay**,
then one Gluetun WireGuard connection as the external VPN. Only network
namespaces of gateway/client Pods are configured. OpenVPN provides mutual TLS,
client address allocation, encrypted UDP encapsulation and reconnection without
DHCP, a custom tunnel protocol, a node agent or a Kubernetes operator framework.

A ClusterIP is an OpenVPN **UDP endpoint**, never an IP next hop. The client uses
`vpnlink` as its actual next hop. The Service stays stable when gateway Pod IPs
change; heartbeat timeout causes a new UDP session/source port, expiring the old
kube-proxy conntrack mapping. Protection does not depend on that timeout.

Admission mutates the Deployment template synchronously and then each new Pod;
a native sidecar with a startup probe installs the guard before all user init
containers. A separate validating webhook checks the final injected state.
cert-manager manages TLS certificates. One gateway uses a Recreate strategy;
its temporary loss causes an outage, not a direct-egress fallback.

## Consequences

There are two encryption layers and one trusted root network sidecar per client,
but only one provider VPN. No application proxy awareness is needed. The first
version is IPv4 egress only, with exec probes and a single cluster DNS exception.
Application ingress, general internal Service access, IPv6 VPN egress,
active-active gateways and per-namespace transport identity are deliberately
outside this version. Shared transport credentials mean all enrolled clients
belong to one trust domain. See the security model and test record for limits.
